# 03 · pi-ai（多 provider LLM API）深潜

> 目录：`packages/ai` · 包名：`@earendil-works/pi-ai` · 版本：v0.84.3
> 角色：统一的多 provider LLM 访问层——把约 **46 个 provider 工厂 / 39 份模型目录 / 21 个 API 实现**收敛到一套类型化 API + 流式协议。
> 源码约 23.6K 行。最大文件：`api/openai-completions.ts`（1695）、`api/openai-codex-responses.ts`（1650）、`api/anthropic-messages.ts`（1391）、`api/bedrock-converse-stream.ts`（1325）、`models.ts`（944）、`types.ts`（857）。

---

## 0. 双入口设计（核心架构决策）

pi-ai 有意分成两套 import 面：

| 入口 | 内容 | 用途 |
|---|---|---|
| `@earendil-works/pi-ai`（`index.ts`） | **core only，无副作用**：类型、`createModels()`、provider 工厂、utils，不含生成目录/registry/OAuth 实现/compat | 新代码推荐 |
| `@earendil-works/pi-ai/compat`（`compat.ts`，298） | 旧全局 API 面：api-dispatch `stream()`/`complete()` + env API key 注入 + api-registry + 生成目录读取（`getModel/getModels/getProviders`）+ 各 API 的 lazy 流包装 + 图片生成 | 存量应用无改动迁移 |
| `@earendil-works/pi-ai/providers/*`、`/api/*` | provider 工厂 / API 实现的分模块入口 | 按需加载 |

`compat.ts` 头注释明确：这是**临时兼容层**，待 coding-agent 的 ModelManager 迁移完成后删除。这解释了 coding-agent 大量 `from "@earendil-works/pi-ai/compat"` 的现状——迁移进行时。

## 1. 核心模型抽象：`models.ts`（944）+ `types.ts`（857）

- **`createModels(options)` → `MutableModels`**：模型集合容器（可变，支持运行时增删）。
- **`createProvider<TApi>(input)` → `Provider<TApi>`**：provider 工厂。
- 泛型 `Model<TApi>` / `Api` 贯穿全包，用类型参数区分不同 API 家族。
- 辅助：`hasApi`（类型守卫）、`calculateCost`（按 usage 算成本）、`getSupportedThinkingLevels` / `clampThinkingLevel`（思考级别能力裁剪）、`modelsAreEqual`。
- `models-store.ts`：模型存储；`model-catalog.ts`：目录；`models.generated.ts`（生成）+ `image-models.generated.ts`（684，生成）——由 `generate-models` / `generate-image-models` 脚本从上游数据生成。

## 8. 设计亮点与权衡

**亮点**
- **双入口（core / compat）** 让新旧代码平滑并存，且 core 无副作用利于 tree-shaking 与浏览器 smoke。
- **lazy API 包装**：重厂商 SDK 懒加载，冷启动与打包体积可控。
- **provider/model 目录代码生成**：39 份目录由脚本从上游数据生成，模型更新可自动化（`pi update --models`）。
- **每家独立 OAuth**：订阅制登录（Anthropic/Codex/Copilot/…）与 API key 并存。
- `uuidv7` 等基础能力上移到 ai 供 agent-core 复用，避免重复。

**权衡**
- **provider 爆炸**：46 工厂 + 39 目录 + 21 API，维护面极大；单个 API 文件动辄上千行（openai-completions 1695）。
- **compat 是临时债**：注释已标注待删，迁移未完时 coding-agent 双依赖 core+compat，增加认知负担。
- 生成文件（models.generated / image-models.generated）需与上游数据同步，存在漂移风险（故有 `check:model-data` 校验）。
